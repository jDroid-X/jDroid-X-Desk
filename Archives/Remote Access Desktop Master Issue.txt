Remote Access Desktop: Master Issue Taxonomy and Priority Matrix
For your jDroid-X-Desk project, I would build the issue register as a production-grade engineering backlog covering remote viewing, remote control, unattended access, connectivity, security, performance, and recovery.
The categories below are based on recurring problem patterns documented in public GitHub issue trackers for open-source remote access projects, including RustDesk, MeshCentral and xrdp. These are representative examples, not a claim that every issue occurs in every product.
For example, public reports describe black screens after connecting, sessions freezing after inactivity, logout leaving unusable sessions, resolution changes breaking layout, and devices appearing offline despite a running agent.

1. Priority definitions
P0
Critical: security or system-wide failure
Unauthorized remote access, authentication bypass, remote session takeover, credential exposure, or a severe vulnerability with credible exploitation risk.
Response: contain immediately, disable affected functionality if necessary, investigate and patch urgently.



P1
High: core functionality unusable
Cannot connect, persistent black screen, remote input failure, repeated crashes, widespread disconnections, or unrecoverable sessions.
Response: prioritize for the next emergency fix or release.



P2
Medium: degraded experience or feature failure
Lag, scaling errors, clipboard or file-transfer failures, audio problems, reconnect issues, or unreliable multi-monitor support.
Response: schedule a fix with a reproducible test case.



 P3 
Low: usability, polish or minor defects
Confusing labels, minor alignment issues, missing shortcuts, incomplete diagnostics or cosmetic defects that do not block work.
Response: batch into regular maintenance releases.



Important: Priority is based on impact, not on how annoying the symptom sounds. A display bug that leaks confidential content can be P0; a display bug affecting only a minor toolbar alignment is P3. A logout problem is P1 if it locks out many users, but P0 if it exposes another user's session.
2. Complete issue register, grouped by category and priority
This register is intended as a master backlog for jDroid-X-Desk. It includes confirmed examples from public issue reports as well as additional engineering risks that a production remote desktop product should test for.
A. Security, authentication and access control
Priority: P0 first, followed by P1 and P2.
ID	Issue / symptom	Priority	Recommended solution
SEC-01	Unauthorized user can control a device	P0	Enforce server-side authorization on every session and control operation.
SEC-02	Authentication or session-token bypass	P0	Use short-lived, scoped tokens, validate every request, rotate credentials and revoke sessions on logout.
SEC-03	Session hijacking or token leakage	P0	Use TLS, secure cookies, token redaction in logs, CSRF protections where applicable and session binding where appropriate.
SEC-04	Remote access remains available after logout	P0/P1	Revoke server-side session state and terminate associated control channels. Test browser Back, refresh and reused URLs.
SEC-05	Weak passwords or brute-force attacks	P1	Rate-limit attempts, apply exponential backoff, alert on suspicious login activity and support MFA.
SEC-06	MFA failure or remembered-device state breaks	P1/P2	Test MFA enrollment, recovery, token expiry, server restarts and persistent-cookie encryption keys.
SEC-07	Permission escalation between users or devices	P0	Apply least-privilege authorization to device groups, files, terminals, clipboard and administrative operations.
SEC-08	Unattended access enabled without clear consent	P0/P1	Require explicit provisioning, authenticated enrollment, visible access policy and auditable revocation.
SEC-09	Remote-control session has no audit trail	P1	Log actor, target device, start/end, authorization result and sensitive actions. Restrict log access.
SEC-10	Credentials, clipboard contents or secrets leak into logs	P0/P1	Redact secrets by default, sanitize input and enforce retention and access controls.
Public examples include a reported idle-timeout configuration that allowed a user to return to an apparently logged-out session, and authentication failures involving two-factor authentication. These illustrate why authentication, timeout and revocation must be tested as a complete lifecycle, not as isolated screens.

B. Connection, network and session reliability
ID	Issue / symptom	Priority	Recommended solution
CON-01	Cannot connect to remote device	P1	Show separate diagnostic states for DNS, TLS, authentication, signaling, NAT traversal and agent availability.
CON-02	Device shows offline while agent is running	P1	Implement heartbeats, server-side connection leases, stale-state expiry and agent reconnect with backoff.
CON-03	Connected but screen is black	P1	Check capture initialization, desktop/session selection, permissions, codec startup and first-frame delivery.
CON-04	Session freezes after inactivity	P1	Add heartbeat and idle diagnostics, test power management and recover the capture/transport pipeline without losing session state.
CON-05	Unexpected disconnections	P1	Detect transport loss, preserve session identity and reconnect automatically with bounded exponential backoff.
CON-06	Reconnect creates a new session instead of resuming	P1/P2	Separate persistent remote-session identity from temporary transport connections.
CON-07	Relay works but direct P2P fails	P2	Diagnose NAT type, firewall rules, ICE/STUN/TURN or equivalent traversal failures; fall back to relay.
CON-08	Works on LAN but fails over the internet	P1	Test reverse proxies, TLS termination, IPv4/IPv6, firewall rules, port mappings and WebSocket upgrades.
CON-09	Authentication succeeds but desktop channel fails	P1	Use independent, observable states for authentication, signaling, control and video transport.
CON-10	Agent reconnect loop or stale connection	P1	Use jittered backoff, connection leases, health checks and bounded restart policies.
CON-11	Network switching breaks an active session	P2	Detect network changes and re-establish transport without duplicating sessions.
CON-12	Proxy or server restart disconnects every user	P1	Add reconnect support, graceful server draining, session resumption and health checks.
Examples: MeshCentral has reports of agents appearing offline despite connectivity, while xrdp reports describe sessions freezing after inactivity and black screens on reconnect.

C. Display, screen capture and rendering
ID	Issue / symptom	Priority	Recommended solution
DSP-01	Entire remote screen is black	P1	Verify desktop capture permissions, active display/session, frame acquisition and renderer initialization.
DSP-02	Black screen until mouse moves	P1	Send an initial full-frame refresh after connection and after returning from suspension.
DSP-03	Frozen or stale image while input still works	P1	Monitor frame age, restart stalled capture/decoder components and request a keyframe/full refresh.
DSP-04	Black rectangles, ghosting or partial refresh	P1/P2	Validate dirty-region updates, buffer lifetime, frame ordering and full-frame fallback.
DSP-05	Resolution change crops desktop or taskbar	P2	Recalculate remote dimensions and viewport bounds after each resize; verify all edges.
DSP-06	Scaling is blurry or stretched	P2	Separate source resolution from viewer scaling, preserve aspect ratio and use appropriate resampling.
DSP-07	High-DPI scaling causes incorrect mouse position	P1/P2	Convert coordinates consistently across physical pixels, logical pixels, scaling and remote desktop coordinates.
DSP-08	Multiple monitors show the wrong screen	P1/P2	Maintain stable monitor IDs, explicit monitor selection and topology-change detection.
DSP-09	Multi-monitor layout has gaps or overlaps	P2	Validate monitor rectangles, origins, scaling factors and supported display arrangements.
DSP-10	Display breaks after sleep, lock or unlock	P1	Re-detect displays, reacquire capture resources and test locked versus unlocked desktop sessions.
DSP-11	Screen capture fails under a different session or service mode	P1	Test interactive-agent and service modes separately; select the appropriate OS capture mechanism.
DSP-12	Video corrupts on high-resolution screens	P1/P2	Test codec compatibility, GPU/CPU paths, buffer sizes and adaptive quality.
These are grounded in reports of black screens, reconnect rendering defects, resolution changes and multi-monitor scaling issues across MeshCentral, xrdp, RustDesk and FreeRDP.

E. Performance, speed and response time
ID	Issue / symptom	Priority	Recommended solution
PERF-01	Slow connection establishment	P2	Measure DNS, TLS, authentication, signaling and first-frame latency separately.
PERF-02	High mouse or keyboard response time	P1/P2	Reduce input queueing, prioritize control messages and measure round-trip latency.
PERF-03	Video lag or low frame rate	P2	Use adaptive frame rate, bandwidth-aware encoding and efficient dirty-region updates.
PERF-04	CPU usage stays high when screen is idle	P2	Use change detection, event-driven capture and adaptive frame polling.
PERF-05	Memory usage increases over time	P1/P2	Profile long sessions, dispose frames and buffers, bound queues and detect leaks.
PERF-06	Network bandwidth is excessive	P2	Adapt resolution, frame rate and codec quality to available bandwidth.
PERF-07	Relay server becomes a bottleneck	P1/P2	Monitor relay capacity, queue depth, CPU, bandwidth and connection distribution; scale horizontally.
PERF-08	Poor performance on older computers	P2	Provide a low-bandwidth mode, CPU-efficient codecs and adjustable visual effects.
PERF-09	High-resolution or multi-monitor sessions overload the device	P2	Adapt per-monitor capture quality and limit unnecessary frame encoding.
PERF-10	File transfer slows or blocks remote control	P2	Separate data and control queues, apply backpressure and cap concurrent transfer resources.
PERF-11	Delayed screen updates despite low ping	P2	Measure capture-to-encode, network, decode-to-render and queueing time separately.
PERF-12	Application becomes unresponsive under load	P1	Keep UI and control loops non-blocking, use bounded queues and implement overload recovery.
Engineering target: measure p50, p95 and p99 input-to-visible-response latency, time to first frame, reconnect duration, frame age, CPU, memory and bandwidth. Set numeric acceptance targets after measuring representative LAN, WAN and low-bandwidth environments rather than choosing arbitrary figures.

FILE-08	Permissions prevent reading or writing files	P2	Report access-denied errors clearly and respect the remote user's permissions.
FILE-09	File transfer requires leaving the desktop screen	P3	Offer integrated drag-and-drop or contextual transfer where platform APIs permit.
FILE-10	Path traversal or unsafe file destinations	P0	Canonicalize paths, restrict destination roots and reject traversal or unauthorized paths.

G. Logout, locked screen, screen off and power states
This deserves its own category because a remote desktop can be connected successfully while the actual computer is no longer in a state that can be captured or controlled.
ID	Issue / symptom	Priority	Recommended solution
LIFE-01	User logs out and remote session becomes a black screen	P1	Detect session termination and return to a clear disconnected or login-screen state.
LIFE-02	Logout leaves orphaned background processes	P1	Clean up session resources and verify the OS session actually terminates.
LIFE-03	Session cannot reconnect after logout	P1	Separate authentication state from desktop-session state and support a clean new session.
LIFE-04	Client laptop screen turns off	P2	Determine whether the OS suspended, locked or merely blanked the display; adapt capture and reconnection behavior.
LIFE-05	Remote computer screen turns off	P1/P2	Handle capture-source loss explicitly; do not assume screen-off means the network or agent is offline.
LIFE-06	Remote computer enters sleep	P1	Detect unreachable/suspended states and support Wake-on-LAN where hardware and network allow it.
LIFE-07	Screen lock prevents viewing or control	P1/P2	Support only the authorized lock-screen capture and input paths permitted by the OS and security policy.
LIFE-08	Switching Windows users disconnects control	P1/P2	Detect active-console and session changes, then reacquire the authorized desktop.
LIFE-09	Remote restart causes permanent offline status	P1	Use a persistent service, startup recovery, health checks and bounded reconnect retries.
LIFE-10	App is closed on the client but remote session remains active	P2	Detect client disconnect, apply configurable grace periods and release resources safely.
LIFE-11	Client browser refresh loses the session	P2	Restore authorized session state safely or provide an explicit resume/reconnect action.
LIFE-12	Idle timeout is confusing or inconsistent	P1/P2	Distinguish account logout, remote-control disconnect, OS lock and session termination.
There are documented xrdp reports of logout producing a black screen and a lingering session, as well as inactivity-related freezes. The correct solution is not simply to disable every screen saver or timeout: it is to model power, display and login states correctly.

3. Cross-category priority summary
The same underlying failure can affect several modules. Use this table to decide which engineering team should investigate first.
Priority	Issue groups to address first	Exit criteria
P0	Security, authorization, session isolation, credential leakage	No known critical access-control defect; security tests pass.
P1	Connect/disconnect, black screens, input, session recovery, agent health	Core remote-control workflows pass reliability tests.
P2	Latency, display scaling, clipboard, file transfer, audio, multi-monitor	Feature-specific acceptance tests pass and performance is measured.
P3	Cosmetic defects, toolbar polish, convenience improvements	Usability review passes and no core workflow regresses.
The numbers above are recommended engineering priorities for your product, not the official severity labels assigned by the projects cited.
4. Recommended issue-management workflow for jDroid-X-Desk
Use one standard record for every defect, feature gap or performance complaint. That makes the backlog actionable instead of becoming a long list of symptoms.
Standard issue record
Required fields for every issue
1. Issue ID and category: for example, DSP-03, display rendering.
2. Priority and impact: P0 to P3, number of users affected and security impact.
3. Environment: client OS, remote OS, app/agent/server versions, browser, network type and monitor setup.
4. Reproduction steps: exact steps, expected result and actual result.
5. Diagnostics: timestamps, correlated logs, CPU/memory usage, network statistics and relevant screenshots.
6. Root cause: confirmed cause, suspected cause or unknown. Keep these separate.
7. Solution: proposed fix, owner, dependencies, regression test and rollback plan.
8. Acceptance criteria: measurable conditions required before marking the issue resolved.

5. Example of a complete issue with a solution
DSP-03: Connected but frozen screen
P1 · High

Problem: The client connects successfully and mouse input reaches the remote machine, but the displayed screen remains black or frozen.
Possible causes to investigate
- Screen capture has stopped producing frames.
- The encoder or decoder has stalled.
- The renderer is not refreshing the screen.
- A reconnect failed to request a full frame.
- A desktop-session or permission change invalidated capture.
Implementation and recovery plan
1. Record the time of the last captured frame, encoded frame, received frame and rendered frame.
2. Detect stale frames independently of the transport connection state.
3. Attempt a bounded full-frame refresh and capture-pipeline recovery.
4. If recovery fails, restart only the failed component when safe, or reconnect the session with a clear status message.
5. Preserve session identity and avoid repeatedly creating duplicate sessions.
6. Add a regression test covering initial connection, idle periods, resolution changes, screen lock and reconnect.
Acceptance criteria
- The client never reports a healthy visual session when no new frames are arriving.
- A recoverable capture failure restores the display within the agreed recovery target.
- An unrecoverable failure produces an actionable error rather than an indefinite black screen.
- Repeated recovery attempts do not leak memory or create duplicate sessions.
